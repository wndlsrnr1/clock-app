# Data Tab Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move JSON backup/restore from the calendar footer into a third top-level `데이터` tab without changing backup domain/application/platform behavior.

**Architecture:** This is a presentation ownership change. Backup use cases already exist in `RhythmAppServices`, and `DataManagementPanel` already owns the import/export UI, so the implementation should reuse that component instead of rebuilding backup logic. `useTodoApp` currently owns page state and backup UI state; for this small change, extend its `AppPage` union to include `"data"` and keep backup actions in the same view model to avoid a broad state refactor.

**Tech Stack:** React, TypeScript, Vite, Vitest, Testing Library, i18n JSON catalog, existing CSS tokens.

---

## Critical Review And Reflection

The proposal is directionally correct because `데이터 관리` handles global app data, not only calendar todos. Keeping it below the calendar makes the calendar page visually busier and gives the wrong information hierarchy.

The smallest safe implementation is not to create new backup domain objects or new services. `DataManagementPanel` already works through `TodoAppViewModel` actions:

- `exportBackup`
- `requestImportBackup`
- `cancelImportBackup`
- `confirmImportBackup`
- `message`
- `preparedBackupImport`
- `importConfirmationOpen`

The only structural problem is naming: backup state currently lives in `useTodoApp`, whose name is narrower than the feature set. Renaming that hook now would touch a lot of code for little user value, so keep it for this change. A future cleanup can rename it to `useAppDataViewModel` or split backup state into a small `useBackupApp` hook if the data page grows.

The main implementation risks are:

- Existing tests currently assert that data management appears after clicking `캘린더`; these must be changed to click `데이터`.
- `TextCatalog` structural tests will fail unless `navigation.data` is added to both `kor.json` and `en.json`.
- `SegmentedControl` uses generic string values, so `AppPage` must be widened before adding the third tab.
- `CalendarPage` should stop importing `DataManagementPanel`; otherwise the feature remains duplicated.
- Backup import success should still reload today's todos, selected-date todos, and calendar summary even when the import happens from the data page.

```tsx
import type { TextCatalog } from "../textCatalog";
import type { TodoAppViewModel } from "../useTodoApp";

interface DataPageProps {
  todo: TodoAppViewModel;
  text: TextCatalog;

export function DataPage({ text, todo }: DataPageProps): React.JSX.Element {
  return (
    <section className="data-page" aria-labelledby="data-management-title">

}
```

## Acceptance Criteria

- `데이터 관리` is no longer rendered inside the calendar page.
- Top navigation has three app view tabs: `시계`, `캘린더`, `데이터`.
- Data import/export behavior is unchanged.
- Backup import confirmation still protects full replacement.
- Locale catalogs stay structurally aligned.
- No domain, application, platform, or backup adapter behavior changes are required.

## Not In Scope

- Renaming `useTodoApp` to a broader hook.
- Adding backup history.
- Adding settings reset.
- Adding cloud sync.
- Changing backup schema.
- Changing import/export file behavior.
- Redesigning the full page layout.

- Placeholder scan: No implementation step depends on undefined behavior or deferred decisions.
- Type consistency: The only new page value is `"data"`, added to locale navigation, `AppPage`, navigation options, and rendering.
